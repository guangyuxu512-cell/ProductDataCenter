# 自动预检

新商品包写入 PostgreSQL 后，由采集项目的 0009 迁移记录待检查状态；商品库 API 在自身进程内领取检查，无需安装额外程序。原包不被预检修改。自动、单条和批量预检都只向这一个持久队列提交任务，再由同一个 `check_product` 检查，浏览器不另做一套正式判断。抖音商品读取当前数据包中已保存的类目属性；拼多多和尚未确定类目的手动商品使用完整标题和主图获取抖店候选，交给用户确认。确认后的类目写回当前商品，后续保存按当前类目检查，不再次推荐或自行更换。

商品库列表只显示本次启用之后新建或变更的商品状态；历史商品可使用单条或批量预检。状态保存在队列表中，翻页或刷新后继续读取。列表在商品 ID 复制图标后显示未预检、排队中、预检中、通过、待选择类目、待完善项数或失败，不打开批量结果弹窗，也不遮罩整张表。商品保存成功后页面先清掉旧结果并显示排队状态；保存失败与预检请求失败使用不同提示。

每次入队都会增加 `revision` 并清空旧结果。领取任务时还记录 `attempts`；完成写回必须同时匹配商品、revision、attempts 和 running 状态，因此较早请求即使晚返回也不能覆盖新结果。采集、新建、导入或编辑只要提交了新的 `uu_json`，都由同一个数据库触发器进入该队列。手动重试和批量预检使用 `/api/v1/prechecks/run` 对同一队列重排，不创建第二张表或独立 Worker。

正式结果同时返回短文本 `issues` 和结构化 `issueDetails`。结构化项包含 `code`、`message`、`tab`、可选 `fieldId`、`skuIndex`、`skuId`，用于从列表或弹窗定位到标题、主图、类目、具体属性或具体 SKU，例如“品牌未填写”“第 3 个 SKU 价格无效”。编辑中的草稿只即时重算能够本地确定的标题、图片、SKU 和已加载表单字段；保存后仍以队列中的正式后端检查为准。

属性表单按平台实际返回的 `type`、`multiple`、`allow_create` 和 `options` 归一为单选、多选、文本、数字及是否允许自定义。存在平台选项且未允许自定义时，任意输入不能作为有效值保存或使预检通过；允许自定义时以值 ID `0` 保存人工值。已有人工填写值优先保留，来源包只在 ID 或唯一名称可以可靠对应时回填。类目树、属性表和表单规则使用原持久缓存，商品属性值不写入规则缓存；用户通过“更新类目/更新属性”显式刷新。

必填和有效性提示基于已取得的类目表单和当前数据，并不代表抖店已经接受或完成上架。未完善商品仍允许保存。

## 发布顺序

1. 由采集项目的正式迁移入口执行 `0009_product_precheck.sql`。在共享生产数据库操作之前，按仓库发布要求先备份并在隔离恢复库演练。
2. 确认商品库 PostgreSQL 登录角色对 `public.product_prechecks` 有 `SELECT` 和 `UPDATE` 权限；如采集服务与商品库使用不同角色，由数据库管理员按实际角色定向授予。新表触发器由迁移所有者执行，避免普通商品写入角色因缺少队列写入权限而影响商品入库。
3. 部署商品库后设置 `BACKEND_AUTO_PRECHECK_ENABLED=true`。此前默认关闭，原有页面和商品 API 可继续使用。
4. 用单个可回滚的测试商品验证队列、页面结果及 RPA；再验证一次真实新采集，确认没有自动改写包或更换店铺 Session。

暂停时关闭开关并重建商品库服务即可；待检查记录保留，恢复后继续。连接或平台暂不可用时会间隔重试，页面显示等待重试。项目本身不执行迁移。
