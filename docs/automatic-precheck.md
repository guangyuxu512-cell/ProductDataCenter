# 自动预检

新商品包写入 PostgreSQL 后，由采集项目的 0009 迁移记录待检查状态；商品库 API 在自身进程内领取检查，无需安装额外程序。符合既有条件的抖音新采集商品会先按当前类目的真实选项写入默认品牌，再重新入队检查；人工修改后的品牌不被后续预检覆盖。自动、单条和批量预检都只向这一个持久队列提交任务，再由同一个 `check_product` 检查，浏览器不另做一套正式判断。抖音商品读取当前数据包中已保存的类目属性；拼多多和尚未确定类目的手动商品使用完整标题和主图获取抖店候选，交给用户确认。确认后的类目写回当前商品，后续保存按当前类目检查，不再次推荐或自行更换。

商品库列表只显示本次启用之后新建或变更的商品状态；历史商品可使用单条或批量预检。状态保存在队列表中，翻页或刷新后继续读取。列表在商品 ID 复制图标后显示未预检、排队中、预检中、通过、待选择类目、待完善项数或失败，不打开批量结果弹窗，也不遮罩整张表。商品保存成功后页面先清掉旧结果并显示排队状态；保存失败与预检请求失败使用不同提示。

每次入队都会增加 `revision` 并清空旧结果。领取任务时还记录 `attempts`；完成写回必须同时匹配商品、revision、attempts 和 running 状态，因此较早请求即使晚返回也不能覆盖新结果。采集、新建、导入或编辑只要提交了新的 `uu_json`，都由同一个数据库触发器进入该队列。手动重试和批量预检使用 `/api/v1/prechecks/run` 对同一队列重排，不创建第二张表或独立 Worker。

## Worker 首条预检链路

`BACKEND_WORKER_PRECHECK_ENABLED` 默认关闭。启用后，自动预检中已有原类目的抖店商品使用中控分配的设备与本机店铺查询类目属性；商品库不读取店铺 Session，仍使用原有规则生成预检结果。首版不改变手动类目查询、拼多多推荐等其他入口。

商品库每次轮询使用同一商品和 revision 接续中控任务，不能因当前队列 attempts 变化重新请求平台。等待中的 pending/running 分别保持排队/处理中；设备离线导致结果未知时显示“等待设备结果”，继续查询原任务，设备补传后自动完成，不新建平台请求。明确失败显示安全原因，不自动重发；仅在新中控确认平台明确要求重新登录时，沿用当前队列换另一家授权店铺。写回仍使用当前 claim 的 revision 与 attempts，旧商品或旧 claim 不可覆盖新结果。设备返回的字段沿用原来的属性归一化规则，结果上限按 UTF-8 字节校验，超限明确失败、不截断。

原有无品牌回填继续生效；回填会触发新的商品 revision，再由队列处理该新版本。启用前需在隔离环境验证设备、对应店铺、受控签名以及完整结果回传。

服务器部署可复用 `deploy/compose.central.yaml` 作为商品库 Compose 的覆盖配置；该覆盖将 `BACKEND_WORKER_PRECHECK_ENABLED` 显式传入商品 API，未设置时保持 `false`。启用 Worker 预检还需现有自动预检开关开启、中控应用身份及设备授权就绪。发布负责人应先只读统计现有待处理和运行中的队列项，确认启用范围；启用会处理符合条件的既有队列，不得作为无条件批量触发。回退时关闭该开关并按现有流程重建商品 API，保留队列记录。

正式结果同时返回短文本 `issues` 和结构化 `issueDetails`。结构化项包含 `code`、`message`、`tab`、可选 `fieldId`、`skuIndex`、`skuId`，用于从列表或弹窗定位到标题、主图、类目、具体属性或具体 SKU，例如“品牌未填写”“第 3 个 SKU 价格无效”。编辑中的草稿只即时重算能够本地确定的标题、图片、SKU 和已加载表单字段；保存后仍以队列中的正式后端检查为准。

属性表单按平台真实响应的 `additions.ui_type`、`additions.diy_type`、`measure_templates`、`max_input_num` 和选项 ID 处理；不能从字段中文名猜规则。无法完成校验的值保留在商品中，预检显示失败而不是通过，也不在字段旁追加平台未返回的解释。多选旧编码仅在每一段都能唯一匹配当前类目的平台选项时拆分，保存后写回原包。类目树和属性表继续使用持久缓存；不含度量及多选上限元数据的旧版属性缓存首次使用时重新取得并保存一次。

必填和有效性提示基于已取得的类目表单和当前数据，并不代表抖店已经接受或完成上架。未完善商品仍允许保存。

## 发布顺序

1. 由采集项目的正式迁移入口执行 `0009_product_precheck.sql`。在共享生产数据库操作之前，按仓库发布要求先备份并在隔离恢复库演练。
2. 确认商品库 PostgreSQL 登录角色对 `public.product_prechecks` 有 `SELECT`、`INSERT` 和 `UPDATE` 权限；如采集服务与商品库使用不同角色，由数据库管理员按实际角色定向授予。商品库保存、手动重试和批量预检需要插入或更新队列记录；新表触发器由迁移所有者执行，避免普通商品写入角色因缺少队列写入权限而影响商品入库。
3. 部署商品库后设置 `BACKEND_AUTO_PRECHECK_ENABLED=true`。此前默认关闭，原有页面和商品 API 可继续使用。
4. 用单个可回滚的测试商品验证队列、页面结果及 RPA；再验证一次真实新采集，确认没有自动改写包或更换店铺 Session。

暂停时关闭开关并重建商品库服务即可；待检查记录保留，恢复后继续。连接或平台暂不可用时会间隔重试，页面显示等待重试。项目本身不执行迁移。
