# 商品属性、默认品牌、图片组件与公网图片补修记录

日期：2026-11-05。基于当时最新 `main` 做最小修改，继续使用共享 PostgreSQL、现有自动预检队列、持久类目缓存、NAS 商品图片目录和既有发布流程。本文件记录本轮代码、验收和发布；CI、镜像产物或代码提交都不能代替生产运行版本核验。

## 实现范围

- 属性规则读取平台真实 `additions.ui_type`、`additions.diy_type` 和选项 ID。单选、多选、文本、数字、自定义与明确枚举由同一规则驱动前端、保存和预检；平台值优先按 ID 校验，旧显示名称变化不会误判。缺少控制元数据的值保留并显示“规则待核对”。
- 属性缓存格式升为带版本的规则缓存。旧的纯列表缓存因已丢失控制元数据而只兼容失效一次，成功取回真实响应后继续持久缓存；普通打开不反复请求平台。
- 真实只读核查覆盖 60 条旧属性缓存，均缺少控制字段。当前响应确认 `multi_select + diy_type=1` 为可自定义多选、`multi_select + diy_type=0` 为受限多选、`search/select + diy_type` 为单选自定义能力；`measure` 为复合结构，当前保留“规则待核对”，不按字段名猜成普通数字。
- 品牌从当前类目的真实“无品牌”选项取得字段和值 ID。新抖音入库在统一预检 Runner 中默认，新拼多多/手动商品在用户确认类目并保存时默认；用户后来人工编辑的商品不会在后续预检中被改回。历史商品使用显式的一次性 `python -m app.modules.products.brand_batch` 先 dry-run、再备份/隔离验证、最后 apply，仅修改品牌字段并触发既有预检队列。
- 主图和详情图复用 `ProductImageList`，共同提供卡片、预览、本地替换、删除、拖拽反馈和按钮换行；SKU 图复用基础卡片操作但关闭拖拽，保持图片与规格绑定。拖拽只改草稿，保存才写数据库和数据包。
- 商品 ID 与复制按钮组成固定布局组，预检状态位于独立后置区域；状态变长时只压缩状态区域。
- 上传只接受配置的 HTTPS 公网根地址。旧商品库私网图片仅在匹配显式旧根地址和 UUID 路由时改写；平台来源图片保持原样。管理详情、导出和 RPA 数据包共用同一规范逻辑。

## 发布顺序

1. 固定业务提交，完成 GitHub CI 的后端、PG16 集成、前端浏览器和容器 smoke；下载按完整提交 SHA 标记且校验过的 API/Web 镜像。
2. 复用现有数据库备份与隔离恢复流程，核对商品数、测试商品、属性缓存兼容、品牌 dry-run/apply、图片上传、导出和 RPA 读取；ProductDataCenter 不运行共享库 DDL。
3. 核实并复用既有公网 RPA HTTPS 入口，只增加商品图片路径转发；保留当前数据库连接、RPA 配置、中控店铺 Session、图片目录、旧镜像和 Compose 备份。
4. 正式执行品牌批量前再次备份，报告 updated/already/unmatched/failed 数量；找不到真实“无品牌”选项的商品保持原品牌并列入待处理。
5. 部署后以容器实际镜像标签/ID核对 API 和 Web，读取既有商品，实际上传并保存图片，核对管理/导出/RPA 地址一致；最后从非 Tailnet 异地 RPA 实机下载并打开图片。切换或健康门禁失败按已审核流程回退；后续验收失败应保留现场并核实实际运行版本，不把失败直接认定为已回滚。
